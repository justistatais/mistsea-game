# 1. 技术栈与取舍（TECH-01）

## 1.1 本版选择

| 层 | 确定方向 | 版本或约束 |
|---|---|---|
| 游戏引擎 | Godot .NET | 4.7.2稳定版；编辑器、Godot.NET.Sdk和导出模板必须同组 |
| 客户端语言 | C# | 统一规则与客户端适配；不混写两套业务逻辑 |
| 运行框架 | .NET 10 | SDK10.0.401、目标net10.0；保守使用C#12语法起步 |
| 图形模式 | Compatibility | 初版二维、低复杂度特效，不以高端渲染为前提 |
| UI | Godot原生Control体系 | RichTextLabel、TextEdit、Container、ScrollContainer等 |
| 持久化 | SQLite | Microsoft.Data.Sqlite10.0.12，显式SQL，不上完整ORM |
| 制作与编译工具 | .NET Console | 与运行时共享类型和规则；Python保留为独立参考校验 |
| 可选在线网关 | ASP.NET Core10 Minimal API | 一个小服务；游戏离线不依赖它 |
| 协议 | HTTPS＋版本化JSON | 仅语言帮助，无世界写权限 |
| 开发管理 | 单仓库、Git、Git LFS | 源文与JSON可审查，二进制素材走LFS |
| 首发目标 | Windows x86_64 | 其他平台不属于首个发布验收范围 |

官方归档列出Godot4.7.2于2026-08-18发布，包含.NET编辑器与对应导出模板；C#需要.NET版编辑器。[S1][S2] .NET10为LTS，官方当前SDK页面列出10.0.401；版本选择不构成Godot集成已通过的证明。[S3]

`data/toolchain_selection.json`保存所选版本和qualification=selected_not_built_in_this_turn。正式NuGet还原后生成packages.lock.json，记录底层原生SQLite版本、包来源、哈希、漏洞审计结果；本轮不伪造锁文件或已下载二进制哈希。

## 1.2 为什么这样选

本项目同时有2D空间、回合状态、大量文本、精确设备条件、可回档的世界和不可随之回档的学习记录。选择原生引擎负责空间与输入，C#纯规则层负责可测试逻辑，SQLite负责跨实体提交。不是因为别的引擎不能做，而是为了只维护一套业务规则、一套UI主实现和一个本地权威状态。

初版不使用浏览器嵌入承担正文，不把HTML示例当主客户端；不引入微服务、消息中间件、通用ECS框架、分布式数据库、在线联机同步或全量事件溯源。必要的事务回执和诊断日志不等于必须重放开局以来全部事件才能读档。

将SQLite async方法直接await不会自动得到真正异步I/O，Microsoft明确记录其限制。[S5] 本项目用专用单写队列，不能让保存阻塞场景输入。

## 1.3 第一项工程任务T00

在指定工具链下完成：空C#场景编译；SQLite原生库加载、事务与备份；3000词与中英混排编辑；原生中文输入法组合、撤销和快捷键隔离；200%字号；实际读屏最小验证；一段音轨的暂停定位；Windows离线导出；在未装编辑器/SDK的干净机器启动。

这些是开工门槛，不是等内容写完才解决的细节。若原生TextEdit、读屏或目标导出不满足，先形成工具链ADR变更与补救验证，不许Coder自行引入网页内核或默默放弃需求。技术方向已选定，验收仍未发生。

# 2. 一仓库、四个主要程序集（TECH-02）

```text
MistSea/
  docs/                     # 01—13设计、ADR、验收、变更单
  game/                     # Godot项目、tscn、资源、UI与平台适配
  src/Mist.Core/            # 纯C#模型、计算、状态机、受控转换
  src/Mist.Application/     # 命令编排、查询、工作流、端口
  src/Mist.Infrastructure/  # SQLite、文件、HTTP、音频/平台适配
  tools/Mist.ContentCli/    # 转换、校验、编译、发布候选
  services/Mist.Assist/     # 可选ASP.NET网关，不掌管世界
  content/source/          # 可编辑定义和原创资产
  content/authoring_only/  # 答案、未来设定、审稿与标定资料
  content/releases/        # 精确版本构建产物；不手工编辑
  tests/Core/ Persistence/ Content/ GodotSmoke/ EndToEnd/
  reference/               # 历史Python模型；只作测试依据
  build/                   # 构建清单、审计、性能与打包报告
```

依赖方向：Core不引用Godot、SQLite、网络和系统时钟；Application依赖Core及端口；Infrastructure实现端口；game作为组合根接入。服务端可复用经过限定的协议DTO，不引用本地世界存档类。

程序集数量按职责克制，不把12个模块立即拆成12个服务。Godot项目内部也按功能分目录，不建立包含一切的GameManager或单个数万行脚本。

领域代码不得获取Node、NodePath、Control、SqliteConnection或HttpClient。UI不得任意修改实体字典、执行SQL或根据按钮文本决定剧情。

| Progression | 等级、点数、装备、个人账 | 构筑与可用物品 | 工程验收、剧情真相 |

| WorkOrders | 实物预留、交付、安装、岗位容量 | 准备缺项、工作回执 | 个人急救与角色经验 |
| Learning | 实际观察、帮助、材料家族、评价 | 分项证据与复习建议 | 任何冒险权威字段 |

一个真实物品只能有一个归属；一个实体只在所属模块产生状态转换。跨模块由Application命令处理器收集并验证各模块变更，在一次数据库事务里一起提交。UI显示“就绪”是查询结果，不另存一个能覆盖实际条件的ready=true。

构建加入架构检查：Core引用Godot/SQLite时失败；AI模块引用IWorldCommands时失败；展示层直接取得写库接口时失败。这些正式架构测试尚未在本轮C#中执行。

# 4. 身份、版本与时钟（TECH-04）

## 4.1 至少区分以下身份

| 身份 | 含义 | 生命周期 |
|---|---|---|
| DefinitionId | Q-102、R1-S02、H01等作者定义 | 内容中稳定，不以名字改动 |
| DefinitionVersion | 同一对象的精确版本 | 不可原地改正文 |
| ProfileId | 本地玩家档案 | 不要求网络账户 |
| CampaignId | 一次完整冒险起点 | 绑定基础剧情/平衡发布集合 |
| BranchId | 某条实际世界分支 | 只有显式回档产生新分支 |
| InstanceId | 本分支里的船、道具、人物或任务 | 存档保存，不每次加载重造 |
| AttemptId | 一次战斗/解题/写作尝试 | 重试产生新尝试，不等于新奖励 |
| CommandId | 一次提交请求 | 响应丢失重查同一ID |
| SemanticSlot | 某项现实工作单次结算槽 | 跨重新发起命令仍唯一 |
| ReceiptId | 已执行结果 | 是结果，不是UI说成功 |
| LoadContext | 当前打开世界的会话令牌 | 继续、回档、重载或权限边界切换时刷新 |
| DraftId＋Revision | 一份正文与不可变修订 | 不用任务名当文本主键 |

程序内部用类型包装ID；显示用可译名称。不同表里碰巧都是字符串，不意味着可以互相替换。

## 4.2 版本不是一个总数

至少分别记录数据库schema、内容schema、规则版本、发布集合、实体修订、设备配置、测试配置、草稿修订、许可修订、学习删除世代和同意版本。

离港预览绑定船、设备、当前检查、许可、当前提案与加载上下文。字体改动和无关来信不让它过期。每个操作有明确read set，不能把“整个世界有任何变化”当过期条件。

## 4.3 四种时钟

渲染帧只驱动表现与移动插值；领域动作序号驱动合法世界变化；战斗计划槽驱动冷却/盾/普通负面状态；真实时间仅用于保存日期、服务超时、明确记录的复习间隔。暂停阅读时不补算战斗或护送伤害。系统时钟异常不能伪造七天延迟验证。

# 5. 内容从制作稿到运行包（TECH-05）

## 5.1 制作输入与生产格式分开

第3—11部分有九套主要参考JSON形状，本轮登记各自适配入口。`Part03Adapter`至`Part11Adapter`将旧结构映射到统一契约；不把所有JSON原样合并。

旧字段如REWARD-Q-P01-TBD要映射到第七部分实际奖励；无法映射直接报告，不当作0奖励。故事ID、地图ID和材料ID保留；表现位置映射到稳定AnchorId，不直接将0—100地图坐标当屏幕像素。

英文原文导入后按ID＋版本＋正文哈希核对；不通过“导入时顺便润色”改变6.5候选和谜底。

## 5.2 条件使用白名单表达树

支持all、any、not、存在性、类型化相等/数量比较、指定回执、许可、资源与配置一致性等有限运算；返回true/false/unknown/error及解释码。

禁止eval、任意脚本字符串、反射类名、SQL片段或内容内调用文件/网络。unknown和false不能互换；尚未加载的配置不能被当成未安装，更不能默认满足。

效果使用受控类型，如TransferItem、ApplyCalibration、CloseQuest、ReserveResource、RecordConsent。内容定义只能提出白名单效果，并由对应领域重新验证。没有SetAnyFlag和RunArbitraryCode。

## 5.3 三层产物

1. 作者包：完整剧情、参考解、审稿、试测记录，绝不直接给在线帮助或全局搜索。
2. 本地运行包：固定世界规则、必须的本地解法与提示、可展示材料/音频/图像；资料访问由可见性投影限制。
3. 在线请求片段：只有已许可、与当前请求必要的最多六段内容及用户明确提交正文，不含作者答案。

离线游戏的运行规则和完整提示必然存在本机，不能宣称能对拥有机器的玩家绝对保密。此处防的是正常UI与AI误泄漏，不是承诺防逆向的反作弊体系。

## 5.4 发布与安装

编译时执行schema/引用/依赖、事实-解法、资源、音轨、审校、6.5任务级校准与来源检查。正式manifest包含所有文件哈希、大小、类型、规则兼容、校准记录和发布key_id。

首版使用ECDSA P-256 SHA-256分离签名，签的是严格编码后的manifest原始字节；原始字节先验签，再用拒绝重复key的严格解析器读取。公钥随可信程序分发，私钥只在发布环境。签名证明发行来源，不证明内容正确或已达到6.5；签署流水线本身必须检查真实审核权限。

普通数据更新只接受白名单JSON、文本、声音和图像。禁止作为数据更新挂载含脚本的PCK、DLL、C#、GDScript或可执行文件。正式程序版本更新使用单独的可信安装流程。

下载到隔离区，限制文件数量、展开大小、单文件32MiB初值、图片解码尺寸、音频时长；拒绝绝对路径、../、Windows盘符/保留名、反斜杠歧义、大小写碰撞、符号链接、重复ZIP路径和压缩炸弹。检查成功后安装为新的不可变目录，旧包不原地覆盖。

本轮参考程序只检查有限manifest、路径和哈希，不实现签名或完整ZIP解压沙箱。

## 5.5 更保守的初版版本策略

新Campaign绑定一个完整、互相兼容的基础发布集合，世界剧情和战斗规则不后台热混用。各任务再保存其精确依赖。已开始的任务不因更新改变资料或答案。

独立练习库可以发布新的已审版本，但不改写当前剧情。基础发布集合变化通过明确迁移及兼容回归；既有战役可留在已安装旧集合。严重问题按第十一部分隔离与修复，不凭“锁旧包”继续提供已知不可用内容。

# 6. 客户端启动与Godot场景树（TECH-06）

```text
AppRoot
  Bootstrap/PlatformServices
  WorldHost                    # 当前2D地区；最多一个活动世界
  UIHost                       # 六入口、路由、材料与编辑器
  ModalHost                    # 确认、错误、提示栈
  AudioHost                    # 主要录音、词音、环境声
  DebugOverlay                 # 仅开发版、明确隔离
```

启动顺序：用户数据目录→单实例锁→控制账与待删除任务→配置→资料发布集合→档案列表→数据库兼容/完整性→加载稳定世界→构建权限过滤视图→进入场景。不能先显示全部NPC和材料再过滤。

安装资源在res://；玩家数据使用user://解析后的原生目录，不写入Program Files或当前工作目录。[S10] 本项目使用固定自定义目录名`MistSeaArchive`，标题译名改变不丢存档。数据库连接前由平台适配器解析路径，Core不保存机器绝对路径。

Godot的活动场景树不是任意线程安全对象。[S8] 所有节点创建、销毁、焦点、音频实例和渲染变化回主线程。读取大文件、校验哈希、数据库写入和HTTP不占渲染线程；其结果回到受控队列。

单实例锁按ProfileId/本机路径标识。第二个进程只能显式只读或请求安全交接，不能两个进程同时静默写同一份草稿。锁文件存在不代表进程活着，使用OS锁并进行恢复检测。

# 7. 单写队列与命令提交（TECH-07）

## 7.1 展示可以及时，后果不能先假装成功

UI发类型化Command→Application检查会话→加载声明read set→Core生成候选patch→执行单次SQLite事务→提交完成→更新只读投影→主线程表现。

除鼠标光标/本地选中等纯展示状态外，领取、发船、买卖、装备、派工、许可发布均以事务回执为准。不能先动画“成功”再祈祷磁盘保存。

## 7.2 唯一持久写入口

每个已打开档案一个有界串行写队列。Draft自动保存、World命令、学习观察和回执消费经过同一执行器；每项短事务有自己的合法范围。UI不持有连接，数据库同步方法在该工作线程运行。[S4][S5]

连续输入允许合并尚未发出的同稿保存请求，但不能越过已经请求的提交/存档屏障。重要命令与草稿均不应永久饥饿；初值每完成一个重要命令，允许一个到期草稿批次，再处理下一项。慢备份和迁移独立进入安全维护窗口。

准备patch时不直接修改当前共享内存对象。事务失败丢弃patch；事务成功后原子发布新只读快照。连接/磁盘未知状态进入恢复，不能一边显示旧金币一边允许按新余额购物。

## 7.3 幂等的两层边界

第一层：同分支同CommandId必须对应同一个规范请求哈希，重复返回原回执，不同载荷拒绝。

第二层：`(BranchId, SemanticSlot)`唯一。同一现实工作换一个命令ID、换方法或重新打开任务，不多结算。SemanticSlot由受控处理器生成，不由客户端自由指定。

重试/读档后旧未提交点击因LoadContext不匹配被拒绝。查询已经提交的回执另有只读接口，可以在新会话下查结果，而不是盲目重新执行旧命令。

## 7.4 outbox负责表现，不负责二次奖励

状态、结果回执、奖励资格和待表现事件在一个事务写入。表现派发可以至少一次尝试，消费者按事件ID幂等。不能承诺声音恰好播放一次，但必须保证世界效果只记账一次。

若动画已播放但确认保存前程序退出，重播或让玩家跳过都可以；金币、物品与许可不得再变一次。

# 8. Q-102离港事务的完整边界（TECH-08）

## 8.1 预览读取什么

当前民用渡轮实例与停泊状态、合法操作点、Q-101许可、支架归属、备用电池/储备、当前配置、对应测试、玩家确认的当前意思与当前正文/许可引用、规则包、当前LoadContext。

不读取雅思分数、看过几个文件、字幕次数或NPC好感。

## 8.2 一个事务一起执行

1. 验证命令和语义结算槽没有冲突。
2. 验证上述版本/条件仍成立，不重新猜玩家意思。
3. 民用渡轮docked=false；相关入口改为不可进入。
4. 主角与协作角色落到`R1-S02`安全锚点。
5. 支架、电池、导航灯留在船上，不重新回背包。
6. Q-102关闭并生成事实回执。
7. 按第七部分发160经验、60刻币、2个人零件、RE-01单次奖励。
8. 保留材料和正文引用，登记可以显示的Q-103后续入口。
9. 写入待表现离港事件与命令回执，提交。

上述1—9不是九次独立保存。SQL事务提供“全部发生或全部不发生”的边界；SQLite的实现仍依赖操作系统和硬件正确完成其存储职责，不能保证所有设备故障均可恢复。[S6]

本轮参考模型使用简化就绪fixture演示离港事务，不包含真实路径、语义解析、完整授权与导航灯全部组件。正式实现必须接入各模块真实read set。

## 8.3 失效与未知结果

设备变化：重新检查；正文变化：重新确认当前意思；无关设置变化：不失效。离港响应丢失：查当前命令或语义回执，不更换ID再次发船。正式数据库错误与玩家方案不成立采用不同错误类别。

# 9. 本地数据库与实际存储（TECH-09）

## 9.1 一档案一主库，所有世界账在同一事务域

`profiles/<ProfileId>/profile.sqlite`包含该玩家的世界分支、任务、物品、草稿、学习观察与提交回执。它们逻辑上分表/分权限，但不把船、奖励、任务分别存入三个需要协调提交的数据库。

`control.sqlite`保存档案索引、删除世代/范围、同意状态、恢复控制与安全备份指针，不保存全文；不随普通冒险检查点回滚。删除流程采用先记录禁止恢复、再清理数据的可恢复过程，不伪称这两库始终属于同一个原子事务。

## 9.2 SQLite设置

```text
journal_mode = DELETE
synchronous = FULL
foreign_keys = ON
busy_timeout = 5000
写事务 = BEGIN IMMEDIATE
```

选择回滚日志是本项目单写者、小量回合动作、内存读投影下的复杂度取舍，不声称它普遍优于WAL。初版不自动开WAL，避免增加checkpoint、旁路复制和多文件维护复杂度。若未来测得必须换WAL，需ADR及原生库、备份和恢复回归。

SQLite只允许一个同时写事务；BEGIN IMMEDIATE可以在事务开始获取写入意向，仍需处理busy结果。[S6] 超过等待时保留请求状态，不无限重试，不把两次资源预留互相覆盖。

## 9.3 主要表组

| 表组 | 作用与约束 |
|---|---|
| metadata / schema_migrations | 数据库身份、schema版本与迁移记录 |
| branches / checkpoints / save_slots | 世界分支、不可变检查点和用户槽指针 |
| entities | 分支内类型化领域聚合的版本与payload；生产由白名单DTO校验 |
| items / balances | 一个实例一个归属、装备槽唯一、余额不为负 |
| receipts / command_log | 单工作记账与请求去重；必须随分支恢复 |
| outbox | 已提交后待表现/投递记录，不能再发奖励 |
| draft_revisions / draft_heads | 不可变全文版本、分支任务头指针 |
| observations / assessments | 实际学习观察与单独评价版本，不进入世界回档 |
| ai_requests / response_cache | 明确同意、上下文版本、结果路由 |
| permissions / work_assignments | 私人发布范围和真实岗位；具体typed payload由专项模块定义 |
| leases / view_state | 短期会话占用和UI定位，不代替持久工作分派 |

本轮参考SQL只实现有限子集（表名单见sql/001_profile.sql），没有谎称包含全部生产实体字段。完整模块payload schema必须作为相应工作包的完成条件，未定义kind禁止写入，不能永久依赖任意Dictionary<string, object>。

钱、经验、数量和槽序号使用整数；经济表有非负约束与唯一键。长正文不是设备payload；个人受限文本集中进入可删除的正文域，世界回执尽量只保留动作与受控字段，避免删文时还在几十份日志中残留原稿。

# 10. 继续、回档、重试三种恢复（TECH-10）

## 10.1 继续游戏

读取当前分支最近完整状态，刷新LoadContext；不新建任务实例、不重发经验、不重填仍在进行的战斗补给。已有装备与消耗按持久记录恢复。

## 10.2 显式读回某个存档槽

验证检查点与内容依赖后，从该检查点创建新的BranchId，复制当时可回档的世界表、回执与草稿头。旧分支保存为历史，仍可从其槽进入。**不是每次启动都创建分支，也不是给完成任务重新起一个新实例。**

来自检查点前的任务、物品和回执保留；检查点后才发生的离港和奖励不复制。于是读回离港前可以再完成一次，读回离港后不能再领奖。这是不同合法时间线，不是全局兑奖表。

共享Profile级的学习观察不复制、不回退；材料家族与帮助历史继续存在。因此读档既不毁掉世界分支选择，也不冒充第一次学习。

## 10.3 战斗失败重试

这是同一冒险分支内的新Attempt，恢复规定战前域（队伍、战斗局部设备、资源预留），保留既有资料、草稿、已完成的无关任务。不能拿全库备份覆盖来实现，导致正文与其他进展丢失。

需要退出再整备时同样依据第八部分声明范围；奖励只在成功或任务指定结果正式提交后产生，失败恢复不能保留成功奖励。

## 10.4 草稿的特殊处理

正文修订实体保存在profile级可删除域，检查点仅保存当时分支的头指针。显式回到旧时间线时，使用检查点里的稿件/引用作为当前工作；未来分支的文本仍然存在，但不自动投影进过去的任务或NPC知识。

用户可回原分支查看/导出自己较新草稿，或明确选择复制；这需要显式动作与当前权限提示，不能系统自动合并未来证据。简单失败重试则保留本次最新兼容草稿，不要求重写。

# 11. 保存槽、备份与损坏恢复（TECH-11）

## 11.1 检查点包含什么

任务、世界许可与政策、物品与账本、角色构筑、人物位置和认知、工程状态、战斗进行状态、设备配置、单次回执、表现游标、合法位置及当前稿件头引用。记录规则版本与发布集合。

不保存Godot Node引用、线程栈、HttpClient、未执行确认token、输入法预编辑缓冲、屏幕像素焦点和网络连接。学习档案/删除记录/系统设置不放进世界回滚包。

## 11.2 何时保存

6手动槽、5滚动自动槽，重要不可逆阶段另有保护点。进入危险前、成功事务后、合法切换地点和用户请求时登记检查点，合并重复的同状态自动点。自动轮换不覆盖保护点。

写作约500ms去抖保存，正常离页与存档屏障先刷新已提交正文。检查点在稳定动作边界创建；玩家动画中请求保存时完成或停止到最近合法边界，不能序列化半个技能伤害。

## 11.3 数据库备份不是把文件复制一下

采用SQLite Online Backup API；Microsoft.Data.Sqlite也提供对应备份接口。[S7] 在安全窗口将主库一致备份到唯一临时目标，核对完整性、外键、档案身份、schema、必要内容依赖和预期提交序号，再注册为可用备份。

不覆盖最近有效备份后才开始检查；不只复制运行中的数据库主文件；不要求玩家把活库放进云同步目录。

实际文件落盘、目录切换和电源中断语义必须Windows测试；本轮只完成有限SQLite进程中断与一致备份试验，不保证硬盘故障。

## 11.4 恢复顺序

先保留损坏原件用于用户选择的恢复，不执行DROP重建。尝试SQLite正常日志恢复；再做完整性与业务不变量检查；失败则列出合法检查点/备份与时间损失范围。用户明确选择，不静默换档。

schema比当前程序新：拒绝写入，提示需要匹配版本。缺旧内容包：恢复包或显式迁移，不自动把旧规则替成最新。

## 11.5 分支增长与空间

不能永久保留每个无引用中间状态。用户槽、保护点、当前分支、待完成工作和仍被引用的正文/评价为保留根；仅删除不可达的世界副本，记录清理结果，不把仍有回执依赖的行直接截断。

学习记录有独立保留政策，不因世界GC删除；用户主动删除则执行下一节。存储容量门槛与备份数量先按性能目标测试，不是满了就静默覆盖重要存档。

# 12. 删除与备份不能互相抵消（TECH-12）

## 12.1 不同删除范围

删除学习观察/评价：不改变冒险与规范草稿。删除草稿正文：定位该DraftId全部相关版本与评估副本，世界仍保存必要的动作回执。删除整个Profile：释放使用者、取消请求、移除游戏管理的对应资料和备份。

不能删除一张UI卡片就声明删除完成。

## 12.2 删除记录在可回档世界之外

先在control.sqlite写入新的删除世代或指定DraftId删除记录，并标为pending；从此任何读取和晚到反馈都应用此限制。随后在profile.sqlite事务中清理相应内容，并清理游戏管理的缓存/备份，成功后标记applied。

两阶段中断后，启动先恢复清理，不先向UI展示旧数据。恢复旧主库备份时，必须再次套用当前控制账，即使某项删除以前已经applied，也不能因备份恢复而失效。

不将控制账随冒险槽复制回旧版，也不降低epoch。已有profile缺少控制账时暂停正常恢复，进入明确恢复流程，默认不激活旧在线请求或导入旧学习/全文；不能无声创建epoch=0。

## 12.3 实际保证范围

本轮原型验证了学习删除世代、草稿删除标记、晚到反馈拒绝及旧主库恢复后的重新清理。尚未实现所有受管理备份的逐份清理、系统级安全擦除或外部服务删除。

逻辑删除与尽力回收不能保证SSD、系统备份或用户手工导出副本不可恢复。界面说明这些边界，不承诺撤回后供应商从未收到。对外导出默认冒险状态与必要引用，不包含全部个人全文或学习历史；用户明确选择另行导出。

# 13. 草稿、文字偏移与输入法（TECH-13）

## 13.1 独立Draft工作流

一个Branch＋TaskInstance拥有唯一当前稿头；多个页面订阅同一DraftViewModel。写入带ExpectedHeadRevision与LoadContext，使用比较并更新，旧请求不能覆盖新稿。草稿版本全局唯一递增或用稳定revision_id，不能两个分支恰好都叫v4而指向不同内容。

本轮参考按同DraftId全局版本递增处理；重新编辑已删Draft时生成新DraftId，不能“复活”已删除文档。

## 13.2 “已保存”必须来自真实提交

UI本地显示尚未保存/保存中；收到当前稿件版本的持久回执才显示已保存。旧回执只确认旧稿，不把新稿勾绿。

保存失败保留当前编辑缓冲，提供重试和明示导出。正文只在本次内存中时，退出需要警告。500ms去抖与异常约5秒丢失目标是工程目标，不保证系统仍持有的未提交IME候选能恢复。

## 13.3 文本位置不能混用UTF-16和字符数

运行材料采用稳定ParagraphId。选择与评价范围使用Unicode标量索引，左闭右开，同时绑定版本与片段哈希。C#字符串索引是UTF-16代码单元，适配器必须显式转换；不能把emoji/CJK组合后的选区错到另一个词。

正文保存保持原文字符与LF换行规范，不做NFKC或自动“聪明纠错”改变玩家意思。显示层可以按字素集群移动光标，传出范围时映射到约定标量索引。必须测试中英文、撇号、组合音标、emoji和多行引用。

## 13.4 输入状态与暂停令牌

IME候选优先，其后是编辑控件、顶层弹窗、工作区和世界快捷键。用InputRouter与显式输入消费，不让同一回车同时换行和确认离港。组合结束/弹窗退出时设置按键释放屏障，旧按住事件不落入新页面。

多个资料/词典窗口持有引用计数式PauseToken；只释放自己持有的令牌，全部释放后世界才恢复。TextEdit是原生候选控件，但真实IME/读屏能力必须T00与后续真机验收，不因存在某个API就宣称已满足。[S9]

# 14. 场景、位置与迁移（TECH-14）

运行场景继承第三部分ID、操作AnchorId和出口PairId。展示角色移动在主线程；拾取/开门/战斗入口提交时重新检查当前场景、合法到达、距离、权限和危险确认，不能信任UI传入“已到达”。

位置采用场景局部坐标及最后安全锚点，保存时不包含屏幕像素。载入位置落入新版本阻挡时，不随意找一个看起来近但越过剧情门的位置；依据版本迁移表恢复到已经合法到达的安全锚点并提示。

切场景采用准备—提交—显示：后台读取资产，主线程建立未激活场景并验证入口；成功后保存逻辑迁移和安全位置，启用目标场景。资源失败保留旧场景，逻辑已提交后表现失败则按该回执重建目标，不将两边物品重复生成。

换场景不清除机关、物品、已开捷径、NPC工作和资料。非关键装饰可重新生成，规则实体不从场景默认值覆盖数据库。

# 15. 战斗必须是确定性的规则机（TECH-15）

战斗Core不引用动画帧率或网络结果。状态包含遭遇ID、尝试ID、入口快照、规则版本、轮、阵营阶段、计划槽队列、位置、HP/专注/AP、冷却、盾来源与到期、暴露、稳定条/恢复保护、装置、普通状态、急救/耗材预算、设备配置和已声明敌方计划。

按第八部分采用我方阶段→敌方阶段、主角3AP、援助2AP、固定ID同序、同根多段合并。先生成纯结果，再提交该稳定动作的全状态与摘要，然后播放。动画中断后恢复该动作已提交结果，不再扣费用。阶段变化是同一个Encounter，不新建配发。

金额数量使用整数，技能系数在数据中用整数万分比；C#计算使用明确的decimal算术与规定位置的Floor，不用float随意累积，不改变第七部分最终取整规定。溢出/不合法系数必须报内容错误。所有实现使用同一规则版本与测试向量。

战斗默认无随机未命中与独立暴击。事件抽选若需要随机，使用明示算法/种子/状态，存入对应实例，不使用全局Random或系统时钟；不能读档生成新奖励表。

第八部分的长战11—16回合、混合路线容错和28级终章未验证继续列为阻断扩大生产的风险。本部分不通过友情倍率或更高等级假装解决。

# 16. 人物、岗位与事件占用（TECH-16）

持久工作分派与临时前景租约分开。人物身份和岗位唯一性属于People/WorkOrders；打开对话取得的lease属于当前LoadContext。加载后清理旧会话lease，不清空已经派工的工程队。

一次事件取得所需人物、位置、物件时全部成功或全部不取得，按固定资源ID排序，禁止长期持有半套资源互等。写作/确认/战斗输入保护优先于新事件推荐；暂停只释放适合释放的前景占用。

对话检索使用可见性投影：世界事实、人物知道、玩家取得、当前允许发布四层分别判定。一个普通值班员可代收合法请求，不能替当事人同意见面或公开姓名。

工作单预留、实物归属、岗位容量和接受的当前协议版需在同一profile事务内核验。完成运输不是完成安装，完成安装不是试运行通过。资源分池和单次任务奖励与第七部分一致。

# 17. 学习证据与AI网关（TECH-17）

## 17.1 学习观察不是世界回执

观察至少包含Profile、来源分支、Attempt、材料/家族/版本、能力、模态、支持范围、已见同事实、时间条件、正文版本与评价来源。重复消息以观察ID和实际尝试键去重；重新评分增加评价版本，不增加一次作答。

只有UI实际展示/音频真实播放事件可以说明接触，素材被预加载不算已阅读。记录暂不可写时仍允许基础帮助，但本次独立条件标为不完整，不默认独立成功。

## 17.2 单一可选网关

采用ASP.NET Core10 Minimal API，提供版本化解释、写作反馈与意图候选接口。生产运行时模型适配器默认Disabled；第一可玩版允许明确Mock/Offline，不假装真实模型已经通过第十一部分语义评测。

供应商选型必须以已有六类以上语义/越权样例扩展评测、数据保留能力、错误率和成本为依据，需正式评测报告才能启用；不是让Codex自由猜一个模型名字。协议和部署技术已固定，实际供应商尚无已验证结论。

服务端保管密钥；客户端只持短期会话凭据和明确许可。联网不要求玩家创建账户，匿名安装会话仍需服务端限流、额度与滥用控制；写进客户端的“公共API secret”不是保护。应用退出后本地游戏继续，网关不运行任务后台模拟。

## 17.3 请求与响应

请求带request_id、功能、协议版本、资料片段、草稿版本、许可/同意与删除世代、帮助范围和客户端关联标记。客户端只发送必要内容，服务器不接收整份世界存档、完整剧情库或所有私人记录。

默认最多六段上下文、最多三项主要反馈和八项展开反馈，最多两次尝试；继承第十一部分。建议单请求正文UTF-8上限64KiB，服务等待约30秒为初值，超限说明原因并提供本地路径；不能改成玩家写作倒计时。

三个接口均只返回不可信候选，不持有IWorldCommands。响应在完整缓冲、结构/长度/来源/当前许可检查之后才显示；未审核内容不直接流式出现。正式band输出默认关闭。

## 17.4 回调路由

当前草稿/分支/许可匹配→当前反馈；正文已更新→旧稿反馈；读档/分支变化→只入有来源的历史视图；权限撤回/删除世代变化→拒绝写回。缓存键包含Profile、内容、目的、帮助范围、许可、正文与模型/提示版本，不跨人共享私人结果。

请求超时只说明服务不可用，不表明世界行动失败。Provider测试、费用审核与删除策略属于正式部署前的独立验收，不能用Mock通过冒充。

# 18. 数据迁移、更新与删除的顺序（TECH-18）

## 18.1 数据库迁移

不直接在唯一原库上做未知破坏性升级。锁定写入→SQLite一致备份/候选副本→迁移候选→schema/外键/业务/删文记录检查→合成恢复测试→安全切换当前数据库generation→保留上个可恢复版本。

迁移按N→N+1显式脚本，记录源schema和脚本哈希；禁止下行写入与未定义跳级。SQLite事务中的DDL失败保持旧结构，但候选切换仍需文件/控制指针的恢复设计。

本轮示例在副本执行一个小版本迁移并注入失败，未实施未来真实游戏每版迁移器。

## 18.2 内容迁移

内容版本、设备配置、文本位置、测试证明和NPC知识不是同一件东西。迁移必须声明哪些状态保留、哪些证明失效、哪些段落可映射。无法精确匹配就保留来源并提示，不把旧高亮绑到碰巧同样长度的新句子。

不因变更素材ID就重发奖励、重新计算“首次阅读”或复活删除正文。

## 18.3 顺序

读取控制账及删除任务优先于旧库展示；迁移候选也应用当前删除约束；内容集合检查先于世界实例恢复；世界恢复先于NPC与资料投影；清理旧确认与网络会话先于可操作UI。

# 21. 性能、容量与制作规模（TECH-21）

以下是待验证预算，不是最低配置或实测结果：在选定的Windows11 x64参考机（4核/8线程、16GB、SSD与集显）测量正常2D场景60FPS目标；菜单无磁盘工作时响应约100ms以内；常规小事务提交p95约150ms以内；明确保存约1秒目标；大内容载入显示进度并可取消。

大字模式与1000条资料目录、长达3000词草稿和多次草稿修订纳入性能用例。画面性能与学习时间不能混计；一秒完成脚本战斗不代表真实玩家一秒完成战斗。
